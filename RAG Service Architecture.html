RAG Service Architecture

One FastAPI process manages datasets and documents, indexes them into a pgvector table per dataset, and answers questions over them. Parsing runs in separate containers. Embeddings and answers go through an external LiteLLM proxy with the caller's own key.

Status: everything below works end to end against a mocked LiteLLM. The real LiteLLM has no embedding model registered yet (as of 2026-11-04), which blocks verification with real embeddings.

  • Code in this repo
  • Runs in docker-compose.yml
  • External service

Components

Requests arrive through a gateway that handles authentication. Inside rag-api, indexing runs on in-process background workers while search and query run inline in the request. Every component reaches outside the process through one of four adapters held in AppState.

Indexing a document

Uploading is synchronous; indexing is a job. The job walks four stages and reports them in stage and progress, so a client can poll GET …/jobs/{job_id}.

  1. 1Upload

    request

    Streams the file to tmp/, enforces MAX_UPLOAD_MB (100) and computes sha256. A dataset keeps one copy per sha256. The original moves to originals/{dataset}/.

    POST …/documents · BlobStore

  2. 2Queue

    queued

    An index_jobs row is written and the job id goes on the in-process queue. The caller's key stays in the runner's memory, keyed by job id.

    index=true or POST …/index · JobRunner

  3. 3Parse

    parsing · 0–40%

    Markdown and text skip parsing. Other files go to Docling or MinerU over HTTP, gated by that parser's semaphore. A cached result for the same parser and options is reused unless force_reparse is set.

    ParserRegistry · parsed/{doc}/{cache_key}/

  4. 4Chunk

    chunking · 40–45%

    Splits the markdown by headings to get a section path, re-splits large sections by sentence at the dataset's chunk size and overlap, and maps each chunk back to its page.

    services/chunking.py

  5. 5Embed

    embedding · 45–90%

    Batches of 64 chunks go to LiteLLM with the dataset's model and document input type. Each vector's length must match the dataset's dimension.

    providers/embeddings.py

  6. 6Store

    storing · 90–100%

    New nodes, tagged with this job's id, go into the dataset's vector table. Then the document's nodes from other jobs are deleted, so search never sees a gap.

    VectorStoreManager · vectors.data_ds_{id}

Job progress to scale. Embedding moves smoothly batch by batch across 45–90%; the other stages jump at their boundaries.

Failure or cancel. The job's own nodes are deleted and any earlier index of the document stays searchable. The document returns to indexed if it had one, otherwise failed (or uploaded when a queued job is canceled).

Server restart. Keys are never persisted, so queued and running jobs cannot continue. On startup they are marked failed with "interrupted", and the client resubmits with its key.

Answering a question

POST …/search stops after the vector lookup and returns scored chunks. POST …/query continues to an LLM and returns an answer with [n] citations, either as one JSON body or as Server-Sent Events.

Errors before the first byte. The stream's first chunk is read before the response starts, so a bad key, an unknown model or an unreachable gateway still returns a normal HTTP error (502 upstream_auth_failed, 504 upstream_timeout, …). Later failures arrive as event: error.

What done carries. The citation numbers found in the answer and the token usage reported by LiteLLM. The JSON mode returns the same fields together with the answer and the sources.

Design decisions

Authorization lives in the gateway
rag-service authenticates no one. Every dataset-scoped path starts with /v1/datasets/{id}/, so a gateway can authorize by prefix, and ids from another dataset return 404.
The caller's key, never stored
Each request carries X-Model-API-Key. The LiteLLM base URL is server configuration only, so no request can redirect someone's key elsewhere. Error messages redact key-like strings.
Embedding model fixed per dataset
Chosen at creation as a LiteLLM model name; its dimension is measured with one call. The hash provider is for local development only.
Answer model chosen per request
model is required on /query and passed to LiteLLM unchanged. Access and cost limits come from the LiteLLM key's permissions, not from a server allowlist.
One vector table per dataset
Datasets can use different dimensions, deletes stay cheap, and each table gets its own HNSW index. Vectors and metadata live in separate schemas of one Postgres.
Filters never reach SQL as text
PGVectorStore's metadata filters interpolate values into SQL, so user filters are applied through customize_query_fn with bound parameters and JSONB containment.
Re-indexing without a gap
Nodes carry the job id. A new job inserts first and deletes the document's older nodes after, and a failed job removes only its own.
Parsers behind HTTP, results cached
Docling and MinerU run as their own containers. The cache key includes the parser options, MinerU's tier among them, so changing the tier invalidates old parses.
